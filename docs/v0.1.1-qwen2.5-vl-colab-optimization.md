# Qwen2.5-VL Colab 학습·추론 최적화 전략

- **상태(Status)**: Accepted
- **작성일**: 2026-09-21
- **전략 버전(Strategy Version)**: `0.1.1`
- **기준 버전(Baseline Version)**: `v3`
- **대상**: `(260908)_baseline_colab.ipynb`
- **적용 결과물**: `(260908)_baseline_colab_optimized.ipynb`
- **실행 환경**: Google Colab 단일 GPU
- **모델**: `Qwen/Qwen2.5-VL-3B-Instruct`
- **학습 방식**: 4-bit QLoRA + Gradient Checkpointing

### 전략 버전 이력

| 전략 버전 | 구분 | 핵심 내용 | 상태 |
|---|---|---|---|
| `v3` | Baseline | Qwen2.5-VL-3B + 4-bit NF4 QLoRA, Gradient Checkpointing, Gradient Accumulation, Drive→`/content` 로컬 학습 | 기준선 |
| `0.1.1` | Optimization | GPU별 BF16/FP16 자동 선택, assistant-only loss masking, DataLoader/I/O 최적화, 잔여 gradient accumulation 처리, batch inference, 생성 token만 decode, Drive checkpoint 저장 | 채택 |

이 전략의 모든 결정과 검증 계획은 **전략 버전 `0.1.1`**을 기준으로 한다. 이후 학습 전략이 변경되면 `0.1.2`, `0.2.0`처럼 버전을 올리고 변경 이유와 성능 비교 결과를 이력에 추가한다.

## 1. Context

기존 baseline v3는 이미 다음 최적화를 적용하고 있었다.

- Qwen2.5-VL 사전학습 모델 사용
- bitsandbytes 4-bit NF4 양자화
- PEFT LoRA
- Gradient Checkpointing
- Gradient Accumulation
- Google Drive의 압축 데이터를 `/content`에 해제한 뒤 로컬 디스크에서 학습

따라서 일반 이미지 분류용 `timm` 모델을 추가하거나 모델 구조를 교체하는 방향은 현재 VQA 과제와 맞지 않는다. 기존 멀티모달 모델과 QLoRA 구조를 유지하면서 실제 병목과 학습 목표를 개선하는 방향을 선택했다.

기존 코드에서 확인한 주요 개선 지점은 다음과 같다.

1. `torch.cuda.amp.autocast(dtype=torch.bfloat16)`과 `GradScaler(enabled=True)`가 GPU 종류와 관계없이 고정되어 있었다.
2. `DataLoader(num_workers=0)`로 이미지 로딩과 processor 작업이 직렬 처리되고 있었다.
3. `labels = input_ids.clone()`으로 시스템 프롬프트, 질문, 선지, 이미지 토큰까지 전부 language-model loss에 포함하고 있었다.
4. Gradient accumulation 마지막 묶음이 `GRAD_ACCUM`으로 나누어 떨어지지 않으면 optimizer step이 누락될 수 있었다.
5. 추론이 sample 1개씩 수행되어 GPU batch 처리 이점을 사용하지 못했다.
6. 생성 결과 전체 prompt를 다시 decode한 뒤 마지막 글자를 찾고 있었다.
7. LoRA adapter가 `/content`에만 저장되어 Colab 런타임 종료 시 사라질 수 있었다.

## 2. Decision

### D1. Qwen2.5-VL + 4-bit QLoRA 구조 유지

현재 문제는 이미지와 질문, 4개 선지를 함께 해석하는 VQA 문제다. 기존 사전학습 VLM과 PEFT 구조를 유지한다.

`timm` 기반 ConvNeXt, EfficientNet 등의 이미지 분류 모델로 교체하지 않는다. 해당 모델들은 이미지 특징만 직접 처리하므로 현재의 질문·선지 텍스트를 함께 해석하는 구조를 별도로 다시 설계해야 한다.

### D2. GPU별 Mixed Precision 자동 선택

GPU에서 BF16 지원 여부를 `torch.cuda.is_bf16_supported()`로 확인한다.

- BF16 지원 GPU: `torch.bfloat16`
- 그 외 CUDA GPU: `torch.float16`
- `GradScaler`: FP16일 때만 활성화

4-bit 연산의 `bnb_4bit_compute_dtype`도 같은 dtype을 사용한다.

이를 통해 특정 GPU에 정밀도를 하드코딩하지 않고 Colab에서 할당된 GPU에 맞게 실행한다.

### D3. 학습 loss를 assistant 정답 구간으로 제한

기존:

```python
enc["labels"] = enc["input_ids"].clone()
```

수정:

- padding token → `-100`
- system/user prompt → `-100`
- visual token이 포함된 prompt prefix → `-100`
- assistant가 출력해야 하는 정답 token과 종료 token만 loss 계산

멀티모달 processor가 이미지 token을 확장하기 때문에 단순 텍스트 길이를 사용하지 않고, `prompt-only` 입력도 동일 processor로 계산하여 prefix 길이를 얻는다.

이 변경의 목적은 모델이 문제 문장을 다시 생성하는 데 학습 용량을 사용하지 않고 객관식 정답 생성에 집중하도록 만드는 것이다.

**주의:** 학습 목적 함수가 달라지므로 v3의 loss 숫자와 v4의 loss 숫자는 직접 비교하지 않는다. 모델 품질 비교는 동일 validation split의 객관식 정확도 또는 실제 평가 점수로 수행한다.

### D4. DataLoader 병렬화와 GPU 전송 최적화

기본값:

```text
num_workers = 2
pin_memory = True
persistent_workers = True
prefetch_factor = 2
```

GPU 전송은 다음 형태로 변경한다.

```python
tensor.to(MODEL_DEVICE, non_blocking=True)
```

목적은 PIL 이미지 로드, chat template 적용, processor 전처리와 GPU 계산의 대기 시간을 줄이는 것이다.

Colab 환경에서 worker 문제가 발생하면 `NUM_WORKERS=0`으로 즉시 되돌릴 수 있도록 설정값을 분리했다.

### D5. Gradient Accumulation 마지막 잔여 batch 처리

기존에는 `step % GRAD_ACCUM == 0`일 때만 optimizer step을 수행했다.

학습 batch 수가 `GRAD_ACCUM`의 배수가 아니면 마지막 gradient가 버려질 수 있으므로 마지막 batch에서도 optimizer step을 수행하도록 변경했다. 마지막 accumulation window의 크기가 4보다 작으면 실제 묶음 크기로 loss를 나누어 gradient scale도 보정한다.

### D6. 추론 Batch 처리

기존 sample-by-sample 추론을 `DataLoader` 기반 batch 추론으로 변경한다.

초깃값:

```text
INFER_BATCH_SIZE = 2
```

OOM이 발생하지 않으면 4로 증가시켜 throughput을 비교한다.

또한 `generate()`가 반환한 전체 sequence에서 입력 prompt 길이를 잘라낸 뒤 새로 생성된 token만 decode한다.

기존:

```text
prompt + generated answer 전체 decode
```

변경:

```text
generated answer token만 decode
```

추론 시간과 불필요한 문자열 후처리를 줄이고 답 추출을 단순화한다.

### D7. 학습/추론 속도 계측값 출력

노트북에서 다음 값을 출력한다.

- 전체 training elapsed time
- optimizer step 수
- inference elapsed time
- inference samples/sec
- validation multiple-choice accuracy

속도 개선 여부는 체감이 아니라 동일 데이터와 동일 seed에서 측정한다.

### D8. LoRA adapter를 Google Drive에 저장

best validation loss 갱신 시 다음 경로에 저장한다.

```text
/content/drive/MyDrive/qwen2_5_vl_3b_lora_optimized
```

저장 대상은 PEFT adapter와 processor다. 전체 3B base model을 다시 저장하지 않는다.

submission은 `/content`와 Google Drive에 모두 저장한다.

## 3. 고려했지만 기본 적용하지 않은 방법

### `torch.compile`

**결정: 기본 비활성화**

PyTorch의 `torch.compile`은 모델 그래프를 컴파일해 처리량을 높일 수 있다. 그러나 현재 입력은 질문 길이와 token 수가 달라지고 멀티모달 processor에 의해 sequence shape도 달라질 수 있다. 가변 shape는 재컴파일을 유발할 수 있으며 첫 실행에는 compilation cost도 발생한다.

또한 현재 모델은 bitsandbytes 4-bit layer, PEFT, gradient checkpointing을 함께 사용한다. 따라서 먼저 eager mode의 안정성과 실제 병목을 측정한 뒤 별도 A/B 실험으로 적용한다.

코드에는 다음 플래그만 남긴다.

```python
USE_TORCH_COMPILE = False
```

검증 시 `False`와 `True`의 epoch time, samples/sec, peak VRAM을 비교한다.

### `timm`

**결정: 적용하지 않음**

현재 문제는 단순 이미지 분류가 아니라 이미지 + 질문 + 객관식 선지를 함께 처리하는 VQA다. `timm`으로 교체하면 텍스트 처리 구조를 새로 설계해야 하므로 기존 baseline의 최적화 범위를 벗어난다.

### Albumentations / Kornia

**결정: 기본 적용하지 않음**

일반적인 horizontal flip, crop, rotation은 자연 이미지 분류에서는 유용할 수 있다. 현재 VQA 이미지가 도표, 글자, 방향성 있는 객체를 포함할 경우 질문의 의미나 정답 자체를 바꿀 수 있다.

데이터 유형을 먼저 확인한 뒤 정답 불변성이 보장되는 augmentation만 별도 실험한다.

### NVIDIA DALI

**결정: 현재 적용하지 않음**

baseline 학습 데이터는 200개 sample만 사용한다. 이 규모에서는 DALI 도입 비용이 더 클 수 있다. 먼저 DataLoader 병렬화 후 GPU utilization과 data wait time을 측정하고 데이터 공급이 실제 병목일 때 도입한다.

### 정답 token 직접 scoring

**결정: 후속 실험**

현재는 `generate(max_new_tokens=2)`를 유지한다. `a/b/c/d` 후보 token의 logit만 직접 비교하면 추론을 더 빠르게 만들 가능성이 있다. 다만 tokenizer에서 각 선택지가 어떤 token sequence로 표현되는지 확인하고 기존 generation 결과와 정확도가 동일한지 검증한 뒤 적용한다.

## 4. Consequences

### 장점

- Colab GPU 종류에 맞는 mixed precision 사용
- 학습 목표가 객관식 정답 생성에 집중됨
- CPU 전처리와 GPU 전송 병목 감소 가능
- 마지막 gradient accumulation 데이터 누락 방지
- batch inference로 GPU 활용도 증가
- 생성 token만 decode하여 후처리 비용 감소
- validation 객관식 정확도로 모델 품질을 직접 확인 가능
- 런타임 종료 후에도 LoRA adapter와 submission 보존

### 비용 및 위험

- assistant-only masking을 위해 학습 collator에서 processor를 두 번 호출하므로 CPU 전처리 비용이 증가한다.
- `num_workers=2`는 Colab 세션과 라이브러리 조합에 따라 worker 문제가 생길 수 있다.
- inference batch size를 과도하게 높이면 OOM이 발생할 수 있다.
- v3와 v4의 loss 함수 범위가 달라 loss 절대값 비교가 불가능하다.

## 5. 검증 계획

동일한 200개 sample과 `SEED=42`를 사용한다.

| 항목 | baseline v3 | optimized v4 |
|---|---:|---:|
| Train samples | 200 | 200 |
| Image size | 384 | 384 |
| LoRA r / alpha | 8 / 16 | 8 / 16 |
| Quantization | 4-bit NF4 | 4-bit NF4 |
| Train batch | 1 | 1 |
| Gradient accumulation | 4 | 4 |
| Inference batch | 1 | 2 → 4 실험 |
| Label loss 범위 | 전체 prompt | assistant answer |
| AMP dtype | BF16 고정 | GPU 자동 선택 |
| DataLoader workers | 0 | 2 |
| Validation metric | loss | masked loss + MC accuracy |

최종 채택 기준:

1. OOM 없이 전체 train / validation / inference 완료
2. 동일 validation split 또는 실제 평가에서 정확도 하락이 없음
3. inference samples/sec 개선
4. 학습 시간이 증가한다면 assistant-only masking의 정확도 개선 폭과 trade-off 비교
5. `INFER_BATCH_SIZE=4`는 batch 2 대비 throughput이 실제 개선될 때만 유지

## 6. 운영 시 조정 순서

속도 문제가 남으면 다음 순서로 조정한다.

1. `INFER_BATCH_SIZE: 2 → 4`
2. GPU utilization과 CPU 사용률 확인
3. CPU 대기가 크면 `NUM_WORKERS: 2 → 4`
4. GPU 메모리가 남으면 train batch size 실험
5. `torch.compile` 별도 A/B 측정
6. 데이터 규모가 크게 증가했을 때만 DALI/Kornia 검토
